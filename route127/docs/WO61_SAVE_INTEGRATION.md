## Save path and sources of truth

`saveSnapshot()` in the shared app serializes the player and flags (including quest state, inventory, equipment, HP/XP, economy, turns, timers, graph and tournament data), world/day, road turn/destination and combat state. `gameplayStageForSave()` filters transient presentation stages, and `loadGame()` restores the snapshot and projects the active UI. Keys are `route127_factory_autosave_v42`, `route127_save_01_v25`–`03_v25`, with V24 fallback; DEVTEST namespaces writes. Casino and banking also have character-keyed journals. R13 captures the relevant journals with snapshot saves and feeds the existing loader in memory through `getSaveData`. Dedicated runtime recovery is still required for closure-local sessions such as an arena exhibition. A saved tournament acknowledgment lives in character flags. Current desktop/mobile PLAYTEST and DEVTEST saves are browser-local. The older online prototype is a separate authenticated save until the current clients use the adapter.

Separate opt-in QA profile and replay tooling come after persistence proof.
4. Stage the PLAYTEST release build independently against the same protocol on separate test storage, then prove migration and rollback with disposable fixtures. For production use separate API deployment/storage and appropriate origin settings. Existing PLAYTEST data is preserved by default, with no DEVTEST write access. No public cutover without owner approval.
5. Rollback candidate by reverting the entrypoint wiring or redeploying the prior private build. Leave browser and D1 records intact. Restore selects cloud state only after identity/revision checks. Production rollback must preserve both pre-cutover local data and cloud records. Establish authoritative action and presence contracts before exposing shared multiplayer/economy.
